# Manual test guide — checking AMYPO by hand

How to verify the product without reading the code: what to open, what to type,
and what you should see. Every check has an id (`S1`, `C4`, `P2`…) so a run can
be recorded and a skipped check is visible.

**The map this document is built around** is the *check map* in section 1: it
says which screen and endpoint each check exercises, so you can pick the subset
that covers the part you care about. Section 1 also explains how to check that
the map itself is not stale.

- **Twin PDF:** `docs/manual_test_guide.pdf` (generated by `python scripts/make_guides.py`,
  or `make guides`). Same check ids. This markdown adds the copy-paste inputs
  and the triage table.
- **Where:** <http://localhost:3000> after `docker compose up -d --build`
- **Accounts:** `admin`, `staff.cse`, `s102` — password `amypo-demo-2026`
- **Time:** ~45 minutes for all 45 checks, ~10 minutes for the smoke path in
  section 10.

---

## 0. Before you start

1. **Docker Desktop must be running.** On Windows, if the engine is not up you
   get `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`
   — start Docker Desktop and wait for the whale to go steady.
2. Start the stack from the project root:

   ```bash
   docker compose up -d --build
   ```

   First start also pulls `phi3:mini` through the `ollama-pull` service. Give it
   a few minutes; the header pill changes from **offline mode** to
   **local model** when it is ready.
3. Prove the two open endpoints (no auth needed):

   ```bash
   curl -s localhost:8000/api/v1/health           # {"status":"ok", ...}
   curl -s localhost:8000/api/v1/resource-status  # ram_available_mb, cpu_load_pct, bandwidth_kbps, api_quota_remaining
   ```

4. Open <http://localhost:3000> in a **private window**, so no earlier session
   survives. The sign-in page has a **Demo accounts** panel that fills the
   username for you.
5. Reset between runs with `docker compose restart backend`. That does not touch
   the database, the corpus or the model. `docker compose down -v` *does* wipe
   the database — do not use it unless you want to re-seed.
6. **Record an observation for every id.** `PASS` with no observed text is not a
   pass. Use the sheet in section 13.

> **Counting rule.** Latency, RAM and bandwidth differ by machine. Judge the
> shape of the behaviour (cache is *far* faster, cost is *far* below
> always-cloud), not an exact millisecond.

## 1. The check map

This is the map: feature → where you see it → what proves it works.

| Check block | Screen | Endpoint behind it | What it proves |
|---|---|---|---|
| S1–S6 | `/login`, header **Sign out** | `/auth/login`, `/auth/me`, `/auth/refresh`, `/auth/logout` | Local login, role from token, redirect-back, sign-out, wrong password |
| C1–C3 | `/` (Chat) | `/ask`, `/ask/trace/{id}` | Grounded answer with citations and a real trace |
| C4 | Chat answer footer → thumbs | `/ask/feedback` | Feedback is stored and reaches retraining |
| C5 | Chat, same question twice | `/ask` + semantic cache | Cache hit returns the same text, far faster |
| C6 | Chat, unanswerable question | `/ask` relevance gate | Abstains instead of inventing; closest records offered |
| C7–C8 | Chat as `s102`, then `staff.cse` | retriever access filter | Cross-student refusal; staff-only documents never reach a student |
| C9 | Chat, non-Latin input | `/ask` language detection | Script detected, answer still English, no crash |
| C10 | Chat toolbar **New chat**, history sidebar | `/ask/history` | Sessions are separate and reopen with sources |
| P1–P3 | `/placement` as `s102` | `/placement/eligibility`, `/skill-gap`, `/what-if` | Criteria table, learning path, what-if deltas |
| P4 | `/placement`, **Download PDF** | `/placement/eligibility/{id}/report.pdf` | A real PDF, own-record only |
| P5 | `/placement` as `staff.cse` | `/placement/match` | Candidate ranking with reasons and closest misses |
| P6 | `/placement`, student id field | `/placement/eligibility` (403) | The server, not the field, decides whose record is readable |
| D1–D2 | `/dashboard` tiles | `/resource-status` | Live RAM/CPU/bandwidth/quota/Ollama, honest degraded states |
| D3 | `/dashboard` **Scenarios** | `/simulate` | Failure modes change routing without crashing |
| D4 | `/dashboard` **Retrain** | `/router/retrain` | Feedback is consumed; no error when there is none |
| D5–D7 | `/dashboard` charts, decision table | `/metrics`, `/router/decisions` | Cost/latency/quality numbers match what you did |
| K1–K3 | `/knowledge` | `/ingest/documents`, `/ingest` | Corpus inventory, incremental re-scan, force re-index |
| E1–E3 | `/evaluation` | `/eval/run` | Live harness run, full run, role gate |
| A1 | `/admin` | `/admin/users` | Account admin: filter, disable, password reset |
| A2, A4 | `/audit` | `/admin/audit` | Audit rows, denied filter, staff sees cohort queries only |
| A3 | `/admin`, `/audit` as `s102` | 403 from API | Direct-URL access is refused, not just hidden |
| A5 | `/api/v1/health` | `/health` | Per-component readiness, no secrets |
| X1–X5 | shell | — | The automated proofs: smoke suite, model pull, guides, status, test suite |

**Using the map.** A 10-minute run is `S1–S4`, `C1`, `C2`, `C5`, `C6`, `P1`,
`P4`, `D1`, `A3`, `X1` — one check per block, which is why the blocks are
ordered that way. A full run is all 45 functional checks (50 counting the map
checks in M1–M5). After changing a feature, run *its row*
plus `X1`; the smoke suite covers every row at API level, so a row that passes
by hand but fails in `X1` means the UI and API disagree.

### How to check the map itself

The map is a claim too, and the cheapest way to catch a stale one is to test
the rows that name a label or a screen:

- **M1** — labels exist. Each label quoted above (**Quick run (40)**,
  **Full benchmark**, **Force re-index**, **Retrain**, **Download PDF**,
  **Denied only**, **Improve all skills (levels)**, **Recompute eligibility**,
  **Closest misses (one criterion short)**, **reset to stable**) should be
  visible on the named screen. A missing one means the map or the UI drifted;
  record which, and fix the document rather than guessing a new click path.
- **M2** — no orphan rows. Every row must name a screen you can actually open
  with a demo role. A row with a screen only an admin can reach, described as a
  student check, is a map bug.
- **M3** — the trace matches the architecture map. Open any answer's
  **Sources and trace** panel and read the trace tab: the stages are
  classify → retrieve → gate → generate → verify. `docs/architecture.md`
  (§ Request flow) and `docs/architecture.png` describe that same order. If a
  stage disappears, the diagram is out of date.
- **M4** — `/health` matches the diagram's boxes. `components` must list
  `db`, `index`, `llm`, `router`. That is the middle row of the component
  diagram; if a component is added or removed, both change.
- **M5** — route names match the routing table. The route badge on an answer
  (**Cache**, **Local model**, **Cloud-sim**, **Offline (extractive)**) must
  correspond to a route in `docs/architecture.md` § Why each route exists
  (`cache`, `local`, `cloud`, `offline_fallback`). A new label in the UI with no
  row in the table is an undocumented route.

A map row whose check cannot be run is a finding: say "map stale at row X"
instead of marking it passed.

## 3. Asking questions (C1–C10)

Ask these as `s102` unless the row says otherwise.

| ID | What to do | What you should see |
|---|---|---|
| **C1** | Ask: `What is the minimum attendance required for exams?` | A direct answer plus citation chips. The footer shows route, latency, confidence %, a tier label, cost `0`, and `grounded n/n claims`. |
| **C2** | Click a citation chip, e.g. `[S1]`. | **Sources and trace** opens on that record. The trace tab lists the real stages: classify, retrieve, gate, generate, verify (map check **M3**). |
| **C3** | Click **Copy** under the answer. | Button reads **Copied** for about a second and the clipboard holds the answer text. |
| **C4** | Click the thumbs-up button in the answer footer. | The thumb turns teal and stays pressed. On `/dashboard`, **Retrain** now reports confirmed feedback instead of *no thumbs feedback yet*. |
| **C5** | Ask the same question again in the same session. | The route badge shows the cache path and latency is an order of magnitude lower. Text and citations match the first answer. |
| **C6** | Ask: `What is the Wi-Fi password for the hostel?` | An abstention: the answer says it could not find support and asserts nothing. **Closest records** are listed; a clarifying question may be offered. |
| **C7** | Ask: `What is the attendance of S101?` | Refused or abstained, with no personal row for `S101`. Then sign in as `staff.cse` and ask again — the cohort answer is allowed. |
| **C8** | As `staff.cse`, ask: `What are the internal notes for the placement officer?` then repeat as `s102`. | Staff get a cited answer from the staff-only document. The student gets no staff-only source and no paraphrase of it. |
| **C9** | Ask a question in Devanagari or Tamil script. | A muted line reads *Experimental: … input detected by script; answered in English.* Retrieval still runs; the answer is expected to be weaker. |
| **C10** | Click **New chat**, then reopen the history sidebar. | Empty state with starter questions. Earlier questions are listed and reopen with their sources. |

## 4. Placement (P1–P6)

| ID | What to do | What you should see |
|---|---|---|
| **P1** | As `s102`, open **Placement** and pick a company role. | An **Eligibility** table: one row per criterion (CGPA, backlogs, attendance, skills) with the observed value and a met/missed verdict. |
| **P2** | Scroll to the skill-gap panel. | Missing skills with the level needed, plus a short learning path. No invented certifications. |
| **P3** | Under **What-if**, raise **Improve all skills (levels)** by one and click **Recompute eligibility**. | `Opens up` / `Lost:` lines and a sentence like *2 roles eligible now → 4 after the change*. Nothing is saved. |
| **P4** | Click **Download PDF**. | A file named `S102-eligibility.pdf` (served from `/placement/eligibility/S102/report.pdf`). It contains the criteria table and the learning path — not a blank page. |
| **P5** | Sign in as `staff.cse`, open **Placement**, pick a role. | **Eligible for …** ranks candidates with reasons, and **Closest misses (one criterion short)** lists students one criterion short. |
| **P6** | As `s102`, replace the student id with `S101`. | No record for `S101` is shown. The Network tab shows `403` on `/placement/eligibility`; the page stays on its loading skeleton (see §11, rough edge 1). |

## 5. Dashboard and degradation (D1–D7)

| ID | What to do | What you should see |
|---|---|---|
| **D1** | As `admin`, open **Dashboard**. | Five tiles (RAM, CPU, bandwidth, quota, Ollama) refresh about every five seconds. Ollama says loaded with a last-reply time. |
| **D2** | Stop Ollama, restart the backend, reload. | Ollama says **unavailable** with a hint naming the start command. Ask a question: it still answers from quoted evidence, labelled extractive. Start Ollama, restart the backend: loaded returns. |

| **D6** | Read the decision table under **Scenarios**. | Each row has query, route, complexity, cost and a human-readable reason. Rows accumulate as you ask. |
| **D7** | Hover the latency bars. | A tooltip gives p50 and p95 in ms for that route. Numbers, not placeholders. |

## 10. The 10-minute smoke path

If you only have ten minutes, run these and stop when one fails:

1. `S1`, `S2`, `S3`, `S4` — login, three roles, redirect-back.
2. `C1`, `C2` — a cited answer and its trace.
3. `C5` — the same question cached.
4. `C6` — an abstention that asserts nothing.
5. `P1`, `P4` — eligibility and the PDF.
6. `D1` — live tiles, Ollama state honest.
7. `A3` — a direct URL refused for a student.
8. `X1` — the smoke suite at API level.

That covers one check from every block, so a complete break in any area shows
up. It is not a substitute for the full 45 before a release.

## 11. Expected oddities — not bugs

1. **A refused student-id edit leaves the skeleton.** In `P6` the page keeps its
   loading pulse instead of printing the `403`; the refusal is real (Network
   tab), the message is missing. Known rough edge, not a data leak.
2. **The cloud leg is simulated.** Quota, price, latency and failure rate are
   constants; nothing leaves the machine. Cost comparisons are model outputs,
   not bills.
3. **Local generation is slow on CPU** (~10–20 s). Cached, tool-backed and
   extractive answers are far faster; the latency tiles are meant to differ by
   an order of magnitude.
4. **Dense retrieval is effectively off** without `sentence-transformers`, so
   hybrid numbers equal BM25 on a default install.
5. **Staff have no PDF control in the UI.** The API supports it; the button is
   only shown for a student's own report.
6. **Vague questions abstain.** *What is the attendance policy?* is below the
   relevance floor; naming the requirement gets an answer. That is the gate
   working.
7. **`docker compose down -v` wipes the database** and the dashboard will then
   report an empty index until `make seed ingest index` runs again.

## 12. If something fails

| Symptom | Likely cause | What to do |
|---|---|---|
| `failed to connect to the docker API … dockerDesktopLinuxEngine` | Docker Desktop not running | Start Docker Desktop, wait for the engine, retry |
| Login page loads, every API call 500s | Frontend cannot reach the backend | `docker compose ps`; check the backend is healthy, then `docker compose logs backend` |
| Header says **offline mode** | Ollama unreachable *or* model not in the container's store | `docker compose up -d ollama`, then `docker compose run --rm ollama-pull` (a host-side `ollama pull` does not reach the container) |
| Dashboard: **model not pulled** | Same as above | `make models` or the compose run above; the card recovers within ~30 s |
| Answers quote evidence instead of generating | RAM below the 900 MB floor with the model resident, or model unavailable | Three-tier fallback working, not a fault — see §11.3 |
| `index is empty` / all questions abstain | Corpus not ingested | `make seed ingest index` |
| `/evaluation` run times out | Full benchmark on a slow box | Use **Quick run (40)**; the full run needs a few minutes |
| Tests are very slow | A local Ollama makes tests use the model | Expected; the suite pins the deterministic stub except `real_model` tests |
| Anything else | — | `docker compose logs backend --tail 100` and record it with the check id |
