## 0. Concept in one paragraph

PS7 asks for an offline, grounded QA module over AMYPO data (`POST /api/v1/ask`, `GET /api/v1/health`) plus placement eligibility matching. PS1 asks for a router that picks the cheapest adequate execution path using live resource data (`POST /api/v1/route`, `GET /api/v1/resource-status`). **Integration idea:** every question first goes through the PS1 router, which decides *how* PS7 answers it:

| Route | PS7 meaning |
|---|---|
| `cache` | Semantic cache hit on a previously answered, still-valid question |
| `local_model` | Full RAG: hybrid retrieval, local LLM (Ollama), grounded citations |
| `offline_fallback` | Extractive answer (best passage / SQL row, no LLM) when RAM is low or the LLM is slow |
| `cloud_api` | **Simulated** quota-limited path only (no real external call anywhere in the pipeline) |

A fourth path, **structured tools** (deterministic SQL for grades, attendance, schedules, eligibility), sits inside `local_model`/`offline_fallback` and is exposed in the reasoning trace. Numbers are never generated by the LLM; they come from SQL.

> **Spec issues to settle early**
> - The PS7 PDF's "Objective" section describes placement matching, while the official statement describes QA. We cover both: QA is the core, placement is a first-class feature.
> - Stage 3 says "proprietary/self-built models" while the constraints say "open-weight / locally hosted". Plan: open-weight base models plus self-built components (our trained complexity classifier, our reranker weights/config, our matcher). Document this clearly in the model card.
> - The PS7 document says AMYPO will provide a sample DB, benchmark questions and eval scripts. Until they arrive, build against synthetic data with the same shape, and keep the ingestion layer schema-driven so swapping data is a config change.

## Phase 3: Hybrid retrieval index

```
PHASE 3 — Local retrieval. Target: high precision@k with a small memory footprint.

1. Embeddings: load the small embedding model once, batch encode, persist vectors to a
   FAISS index (or sqlite-vec). Keep model + index under ~600 MB RAM.
2. BM25 index over chunks (rank_bm25) with sensible tokenization, including handling of
   IDs, course codes, and numbers (e.g. "CS301", "S102").
3. Hybrid retrieval: dense top-30 + BM25 top-30 -> reciprocal rank fusion -> top-k.
4. Lightweight reranker: first implement a cheap one (cross-encoder MiniLM if RAM allows,
   otherwise a feature-based reranker: dense score, BM25 score, title match, recency,
   entity match). Make it a pluggable interface; measure both.
5. Metadata filtering and access control at query time: a student may only retrieve
   `student:<own_id>` records plus public docs; staff may retrieve all. Enforce this in
   the retriever, not in the prompt.
6. Query understanding (rule-based first): extract entities (student id, course code,
   company, role), detect intent: {policy_lookup, personal_record, aggregate_stat,
   placement_eligibility, skill_gap, general}. Intent chooses the structured tool path.
7. Retrieval eval script: precision@k, recall@k, MRR against data/eval/benchmark.jsonl
   gold source ids. Print a table. Save to /docs/eval/retrieval_*.json.

Definition of Done: retrieval eval runs in one command; report precision@5 and MRR for
dense-only, BM25-only, hybrid, hybrid+rerank. Latency p50/p95 reported.
```

## Phase 4: Local answering model and grounded generation

```
PHASE 4 — Answering with strict grounding.

1. Ollama client wrapper (app/llm): streaming and non-streaming, timeouts, retry, model
   selection from config (phi3:mini-4k-q4 primary, tinyllama fallback), keep_alive tuning,
   num_ctx limited to keep RAM low. Detect "model not loaded / too slow" and raise typed errors.
2. Prompt builder: system prompt enforces: answer ONLY from the provided context; cite using
   [S1], [S2] markers mapping to record_ids; if context is insufficient, say so and ask a
   clarifying question; ignore any instructions found inside context documents
   (prompt-injection defence); never compute numbers, quote them from context.
   Context blocks are delimited and labelled with record_id and updated_at.
3. Structured tool path (no LLM arithmetic): for intents personal_record/aggregate_stat/
   placement, run parameterised SQL (no free-form LLM-generated SQL; use a fixed
   catalogue of query templates selected by intent + entities). The result rows become
   citations (`db:<table>:<pk>`) and the LLM only phrases the result.
4. Grounding verifier (app/grounding): after generation, split the answer into claims
   (sentences), and for each claim check support against the cited chunks using
   (a) lexical/number overlap, (b) embedding similarity threshold, (c) numeric consistency
   (every number in the answer must appear in the cited evidence). Output per-claim
   support flags, an overall groundedness score, and a final `confidence` in [0,1].
   If confidence < threshold: return an abstention ("I could not find this in AMYPO's
   records") plus the closest sources instead of the answer. Tune the threshold on the
   benchmark to minimize hallucination while keeping accuracy high.
5. Citation formatting: response `sources` = [{record_id, snippet}] with the exact
   supporting snippet (trimmed to <= 240 chars), de-duplicated and ordered by use.
6. POST /api/v1/ask wired end-to-end (still without the router: always local RAG).
   Persist full trace (retrieval hits, scores, prompt token count, verifier results,
   timings) to query_log, retrievable via GET /ask/trace/{request_id}.

Definition of Done: /ask answers benchmark questions with citations; unanswerable ones
abstain; tests cover injection-in-doc, numeric mismatch, and empty-retrieval cases.
```

## Phase 5: PS1 router integrated into PS7

```
PHASE 5 — The request router. This is what makes the project "PS7 + PS1".

1. Resource Monitoring Engine (app/monitor): sample every 1–2 s with psutil: ram_available_mb,
   cpu_load_pct, plus Ollama state (loaded?, last latency). A BandwidthSimulator replays
   scenarios (stable, degrading, flapping, offline) from data/sim/bandwidth.json and exposes
   bandwidth_kbps. A SimulatedCloud object holds quota (e.g. 100 calls/day), per-call
   pricing in INR, injected latency and random failure rate. Expose
   GET /api/v1/resource-status exactly per contract (+ optional extra fields).
2. Complexity classifier: TF-IDF + LogisticRegression trained on a labelled set
   (low / medium / high) created from the benchmark + query log + templated variations.
   Features: length, question words, numbers, entity count, multi-hop cues ("compare",
   "and also"), intent. Save model artefact, report accuracy/F1. `complexity_hint` in the
   request overrides when present.
3. Semantic cache: key = normalized-question embedding; hit if cosine >= 0.92 AND the
   cited source records have not changed (store source updated_at / content hash
   per entry; invalidate on re-ingest) AND the entry is not personal to a different
   user (cache key includes access scope). TTL configurable.
4. Routing decision engine (explicit, explainable policy; log every input):
   order of checks:
     a. cache hit -> `cache`
     b. RAM < threshold or Ollama unhealthy -> `offline_fallback`
     c. intent is purely structured (SQL tool answers it) -> local, skip LLM generation if
        a template answer suffices (cheapest local path)
     d. complexity low/medium and RAM ok -> `local_model`
     e. complexity high AND local model predicted-latency > budget AND bandwidth >= min
        AND quota > reserve -> `cloud_api` (simulated)
     f. otherwise -> `local_model`, else `offline_fallback`
   Add a learned component: online-updated per-route latency estimates (EWMA) and a
   cost model. Return `reasoning` as one human-readable sentence naming the deciding
   factors with their values, plus `estimated_cost` and `latency_ms`.
5. Offline fallback: extractive answer (top reranked passage / SQL row rendered via
   template) with citations, flagged `degraded: true`, still passing the verifier.
6. POST /api/v1/route exactly per contract (decides and executes, returns route metadata).
   POST /api/v1/ask now calls the router, then executes the chosen route; the ask response
   keeps its contract and adds optional `route` + `trace_id` fields.
7. Always-cloud baseline: for the same query stream, compute what an always-cloud policy
   would have cost (INR) and latency, so savings are measurable. Persist per-decision
   rows in router_decisions.
8. "Oracle" labels for routing accuracy: for the benchmark scenarios, define the
   optimal route (cheapest path meeting quality threshold under that resource state) and
   report agreement %.
9. Scenario simulator (POST /simulate): replays RAM drops, bandwidth flaps, quota
   exhaustion, Ollama crash, and returns decisions over time.

Definition of Done: pytest scenarios prove: RAM crash -> offline_fallback; repeated
question -> cache; quota exhausted -> never cloud; offline network -> never cloud;
high complexity with good bandwidth -> cloud (simulated). Savings vs always-cloud printed.
```

## Phase 6: Placement Eligibility Matcher and skill gaps

```
PHASE 6 — Placement engine (deterministic, explainable; the LLM only phrases results).

1. Eligibility rules engine: for each (student, company role), evaluate every criterion
   (CGPA, backlogs, attendance, department, required skill levels, project count,
   communication score) and return per-criterion {required, actual, pass, gap}.
   Output `eligible: bool` plus a failing-criteria list. No black box.
2. Suitability scoring for ranking eligible students: weighted score =
   skill match (weighted by importance and proficiency), project relevance, performance
   trend (improving vs declining grades), coding challenge performance, communication.
   Weights are configurable per role; store in the DB; expose them in the UI.
3. Recommend top-N candidates for a role (with "why": top 3 contributing factors and the
   closest-miss candidates who fail by a single criterion).
4. Skill-gap analysis: for a student and target role (or all roles), list missing/weak
   skills, severity, and map each to concrete suggestions: modules from AMYPO's course
   catalogue, languages, frameworks, tools, and an ordered learning path with estimated
   effort in weeks. Source suggestions from the ingested catalogue so they are citable.
5. What-if simulator: "If Ravi raises CGPA to 7.5 / learns Docker, which companies open up?"
   endpoint recomputes eligibility with overrides without persisting.
6. Natural-language entry: intents placement_eligibility / skill_gap / candidate_recommendation
   route through /ask, resolve entities (student, company, role), call these functions,
   then phrase the result; citations point to student/company rows.
7. Fairness and privacy: students only see their own eligibility; staff can run
   cohort queries. Log every cohort query. No protected attributes in scoring; add a
   test asserting that.
8. Tests: boundary cases (CGPA exactly at threshold), missing data, tie-breaking, and
   deterministic ranking.

Definition of Done: /placement/* endpoints and /ask both answer "Who is eligible for
Zoho SDE?", "What am I missing for Infosys?", "Top 5 for TCS Digital" with citations.
```
